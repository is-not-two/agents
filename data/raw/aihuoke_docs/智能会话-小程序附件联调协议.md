# 智能会话附件联调协议

## 适用范围

本协议适用于登录后的智能会话。附件上传、发送和历史读取均以 `file_id` 为唯一可信标识；客户端不得把本地路径、临时 URL 或自行声明的文件类型作为服务端判断依据。

## 1. 上传

图片使用 `POST /api/upload/image`，视频使用 `POST /api/upload/video`，普通文档使用 `POST /api/upload/file`。请求使用 `multipart/form-data`，文件字段名为 `file`。

成功响应的 `data` 至少包含：

```json
{
  "id": 101,
  "name": "example.png",
  "uri": "https://media.example.com/uploads/images/example.png",
  "url": "uploads/images/example.png"
}
```

客户端仅保存并在发送会话时提交 `id`。`uri` 可用于上传完成后的本地预览；重新进入会话时必须以历史接口返回的地址为准。

## 2. 发送会话

`POST /api/chat/commonChat` 使用 SSE 响应。新字段为 `attachments`：

```json
{
  "message": "请比较这两张图，并概括视频中的卖点",
  "task_id": "existing-task-id",
  "attachments": [
    { "file_id": 101 },
    { "file_id": 102 },
    { "file_id": 103 }
  ]
}
```

- `attachments` 可为空、单项或多项，顺序即用户发送顺序。包含附件时，`message` 可以为空。
- 后端会校验附件归属，并根据服务端记录判断图片、视频和文档。
- 图片会同文本组装为豆包 Chat Completions 的多个 `image_url` 内容项。
- 视频会同文本组装为豆包 Chat Completions 的多个 `video_url` 内容项（`fps: 1`），同时保存并在历史中预览。视频 URL 必须能被公网 HTTPS 访问。
- 文档继续由服务端解析为文本上下文。
- 旧字段 `file_info` 暂时兼容单附件；新小程序必须改用 `attachments`。

图片理解当前接收 `jpg`、`jpeg`、`png`、`gif`、`webp`。`ico` 虽可上传和预览，但当前不会发送给模型，客户端应提示用户改为 PNG/JPEG 后重试。

## 3. SSE

SSE 帧保持现有 `loading`、`finished` 协议不变。附件不在 SSE 帧重复回传；客户端在本次发送期间保留已上传附件，结束后通过历史接口取得服务端确认的数据。

## 4. 读取历史

`GET /api/chat/chatLogs` 的用户消息新增 `attachments`：

```json
{
  "type": 1,
  "message": "请分析素材",
  "attachments": [
    {
      "file_id": 101,
      "type": "image",
      "name": "example.png",
      "url": "/uploads/images/example.png",
      "preview_url": "/uploads/images/example.png",
      "available": true
    },
    {
      "file_id": 102,
      "type": "video",
      "name": "demo.mp4",
      "url": "/uploads/video/demo.mp4",
      "preview_url": "/uploads/video/demo.mp4",
      "available": true
    }
  ]
}
```

- `image`：显示缩略图，点击预览原图。
- `video`：显示封面或视频卡片，点击播放 `url`；服务端后续返回转码状态时，以该状态展示“处理中”。
- `file`：显示文件卡片并允许按既有行为下载/打开。
- `available: false`：显示“附件不可用”，不得继续请求空 URL。
- 旧记录可能没有 `attachments`，客户端应回退读取现有 `file_info` / `file_urls`，保证升级前会话不空白。

## 5. 小程序改动清单

1. 上传后将每个返回的 `data.id` 添加到本地有序附件列表。
2. 发送时传 `attachments: [{file_id}]`，不再只传第一项 `file_info`。
3. 支持同一消息的文本、多个图片、视频和文件卡片混排。
4. 历史消息优先渲染 `attachments`；刷新与重进会话时不得复用已失效的本地临时地址。
5. 发送前阻止任一仍在上传或上传失败的附件；全部附件成功并取得 `file_id` 后才能发送。
6. 图片、视频 URL 必须能被公网 HTTPS 访问，否则服务端会拒绝发送给模型。
