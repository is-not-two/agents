## 0. 先回要点（TL;DR）

1. **Q2/Q3 关闭了**：设备回带的 `published_media` = 下发 `list` 全量同序同量 → 后端「成功回执条数必须相等」的强校验在视频号上**不会误判成功为失败**。原审计 B2/B2′ 的「成功记失败」路径在视频号上**不成立**。
2. **但 B2 转化为「留痕失真」（R2）**：设备图文只选前 9 张（`MAX_IMAGE_PICK=9`，超出静默截断）却回带全量 → 后端会把「实发 9 张」记成「12 张全部成功」。
3. **B1（回执超时收敛）由 P1 升级为发布链路的唯一兜底**：设备侧 type=14 **无重传、无落盘**，一帧丢失即明细永久 `status=3`。这条必须做。
4. **R1 后端确证为 P0**：`/auto.device/opt` 的「图文/视频演示」会给**真实在线设备**下发同构 type=5，且不带 `read_only` → **真实发布**，且回执因 `material_id=0` 被丢弃、无留痕。
   **决策（2026-10-08）：后端不改**，`isSend=0` 已在下发里，由设备端识别；⚠️ 设备端必须判 `isSend` 而**不是** `isDemoData`（原因见 §2 R1）。
5. **Q8 后端已经是 (A)**：下发前强制 `publish_time <= now`（`DeviceTaskTrait.php:370` + 调度器时间窗），设备"收到即发"与语义一致，`scheduledTime` 仅作留痕；粒度受调度 tick 限制（`task:scheduler` 15s / `auto_task:scheduler` 30s）。

## 2. 逐条回答 R1–R6

### R1（P0）演示/预览链路会真实发布 —— **后端确证：会发生**

证据链（全部在后端仓库内可复现）：

| 环节 | 位置 | 事实 |
|---|---|---|
| 入口 | `app/api/controller/auto/DeviceController.php:49-60` | `opt()` → `DeviceLogic::opt()` |
| 入参 | `app/api/validate/auto/DeviceValidate.php:25-26,91-94` | `device_code` + `account_type∈{1,3,4,5}` + `source∈1..10`；`source=1` 图文演示、`2` 视频演示 |
| 目标账号/设备 | `app/api/logic/auto/DeviceLogic.php:351-367` | 按 `user_id+device_code+account_type` 取**真实** `SvAccount`，并要求该设备在 Redis 在线 |
| 指令构造 | `:462-518` | `type=5`，`publish_platform=$account->type`（视频号=1），`list` 为**真实素材**，`isSend=0`，`isDemoData` |
| 下发 | `:369-377` | `Channel\Client::publish("device.{device_code}.message")` —— 与正式发布同一出口 |
| 演示素材来源 | `:756-776`、`:807-827` | 复用该设备最近一条真实发布明细（`$publish->id = 0`，`task_id` 仍是真实值） |
| 回执落点 | `MediaStatusHandler.php:54-58` | `material_id=0` 查不到明细 → 抛「发布回执未匹配素材任务」→ 整帧丢弃 |

**结论**：设备不认 `isSend`/`isDemoData`，`read_only` 又没下发 → 演示点击 = **真实发布一条**；且因为 `material_id=0`，后端没有任何明细/日志能证明它发过。

**决策（2026-10-08）：后端不改，由设备端承接。** 理由：`isSend=0` 已经在演示 payload 里（图文 `:484`、视频 `:512`），后端无需新增字段。

⚠️ **设备侧实现时必须判 `isSend`（或"`isSend` 键存在且为 0"），不能只判 `isDemoData`**：

| 演示分支 | `isSend` | `isDemoData` | 只看 `isDemoData==1` 的后果 |
|---|---|---|---|
| 降级演示文案 | 0 | 1 | 能拦住 |
| **复用该设备最近一条真实发布明细** | 0 | **0**（`:773`/`:824` 把 `is_demo_data` 置 0 后回填） | **拦不住 → 仍会真实发布** |

即：只认 `isDemoData==1` 的话，第二种分支仍会真实发布，R1 不算关闭。

备选方案（若设备端不愿改）：后端在两处演示 payload 补 `read_only => 1`（2 行），设备会停在「发表」前并回 `status=2`，该回执因 `material_id=0` 被丢弃、无副作用。

> 补充口径：`checkOpt()`（`:289-335`，预览接口）只构造 payload **不下发**，本身不产生真实发布；风险只在 `opt()`。

### R2（P1）图文下发张数收口 —— **同意方向，但不能简单把 12 改成 9**

- 设备侧上限 9（`MAX_IMAGE_PICK`），后端上限 12（`PublishMediaUrlService.php:14`），二者不一致时：**实发 9、回带 12、记账 12**（留痕失真，不判失败）。
- ⚠️ 关键约束：`forDevice()` / `forReceipt()` 是**平台无关**的（同一常量服务视频号/小红书/抖音/快手/朋友圈）。**直接把常量改成 9 会连带把小红书等平台压到 9**。
  - 若产品确认「各平台图文都按 9」（PC 面板 `public/pc/_nuxt/publish-panel.a4303c5a.js` 的 `le=9`、AI 文案 `PublishImageCopywritingService.php:55-57` 都已是 9）→ 改常量最省（1 行），但**上线前必须先抽查历史数据**（>9 的明细会被 `PublishMediaUrlService.php:37-41` 直接判 `status=2`）。
  - 若要保留平台差异 → 应做**按平台的下发上限**（视频号 9），落点在下发选择/校验处，而不是改全局常量。
- 我倾向：**先按平台收口视频号 = 9**，暂不动全局常量；等产品给「各平台图文上限表」后再统一。

### R3（P1）视频终态轮询 100s 偏短 —— **主责在设备侧；后端只做一个可选项**

- 设备侧：把终态轮询窗口按类型放宽（视频建议 ≥5min），并把「上传中/发布中」识别为中间态而不是失败。
- 后端不建议自动重试：设备**无 `taskId` 去重**（Q4），重发 type=5 会**重复真实发布**。
- 后端可选项（需产品定口径）：把 `status=2` 且 `msg` 含「未确认」的失败与「确定失败」在 remark/结果码上区分（例如落 `result_code=uncertain`），供人工判断是否重发。当前一律记 `status=2` + 原 msg。

### R4（P1）回执超时收敛覆盖 `publish_platform=1` —— **接受，改为必做**

设备答复证实 type=14 无重传、无落盘，因此这是「卡在发布中」的**唯一**自愈手段。实施要点（沿用审计 B1 结论）：

1. 平台过滤去硬编码：`KwaiPublishReceiptTimeoutService.php:78-84` 的 `where('account_type', PUBLISH_PLATFORM_KS)` → `whereIn(..., 白名单)`；类名/日志标题（`:117`、`:180`）/调度器文案（`DeviceTaskScheduler.php:306,310`）去「快手」字样；`.example.env:131` 注释同步。
2. `DeviceEnum.php:62` 白名单加 `PUBLISH_PLATFORM_SPH`，**并修正 `:53-61` 的误导注释**——该注释说「只需把常量加进本数组」，但它只开诊断日志，**不会**开收敛。
3. 保持 `:136-147` 的条件更新（避免与真实终态竞态）；`MIN_INTERVAL_SECONDS`/`BATCH_SIZE` 为静态共享，多平台共用一轮扫描，无需改。
4. 风险：SPH 若「设备任务行缺失」，判据只剩 `exec_time ≥ 阈值(600s)`；长视频上传可能被误判。建议 SPH 单独阈值（与 R3 的 ≥5min 对齐）。

### R5（P2）`taskId` 非空 + 重发语义 —— **后端核实：正常路径不会重发同一明细，但有 3 个边界**

| 场景 | 后端行为 | 是否会重复真实发布 |
|---|---|---|
| 正常下发 | 下发后立即写明细 `status=3`（`DeviceTaskTrait.php:423-428` → `setRpaPublishStatus` `:2063-2090`），选择器要求 `status in [0,5]`（`:366`） | **不会**，同一明细不再被选中 |
| 下发→写状态之间进程被杀/DB 写失败 | `:427` 已 publish、`:428` 尚未写状态 → 明细仍 `0/5` → 下一轮重新选中并再发一次 | **会**（设备无去重） |
| 用户「重试/重新发布」 | `device/PublishLogic.php:693-695`（→0）、`:723-725`（→5）显式重排队 | **会**，属用户预期重发 |
| 同一 tick 内 pending/completed 两条路径 | `DeviceTaskScheduler.php:114-120` 先 `checkPendingTasks` 后 `checkRunningTasks`，两条路径都会调用 `rpaPublishTask` | 若同账号同一时刻存在**2 条到期明细**，可能连发 2 帧 → 设备 `StepManager.cleanup()` 打断第一条（**需复核生成器是否会造出这种组合**） |

**后端可做的加固**：把明细状态「占位」提前到 channel publish **之前**（条件更新 `status∈[0,5] → 3` 抢锁，抢不到就跳过），可消掉第 2 行的崩溃窗口。这属于小改动，但会改变现有下发时序，建议与 R4 一起评估。

### R6（P3）`appVersion` 硬编码 `2.4.0` —— **确认属实，低优先**

`DeviceTaskTrait.php:404`（`sphPublishTask` 死代码 `:305` 同值）。设备实为 3.3.10。无功能影响，仅排查误导。建议：抽成常量集中管理，或等设备信息事件里有版本字段后再动态取（当前后端未在发布链路读取设备版本）。
