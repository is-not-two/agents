## 1. 后端 → 设备：下发契约（现状，必须设备端已支持）

出口：`ChannelClient::publish("device.{device_code}.message")`（`DeviceTaskTrait.php:423-427`）

```json
{
  "appType": 1,
  "messageId": 0,
  "type": 5,
  "deviceId": "<device_code>",
  "appVersion": "2.4.0",
  "content": "{\"publish_platform\":1,\"material_id\":123,\"title\":\"文案标题\",\"type\":2,\"list\":[\"https://.../a.jpg\",\"https://.../b.jpg\"],\"isLocation\":0,\"location\":\"\",\"isScheduledTime\":true,\"scheduledTime\":\"2026-09-20 10:30:00\",\"taskId\":\"<32位md5>\",\"body\":\"正文\",\"tag\":\"话题\"}"
}
```

| 字段 | 值 / 口径 | 出处 |
|---|---|---|
| `type` | `5` = `WorkerEnum::RPA_PUBLISHED_POST`「发布笔记」 | `app/common/workerman/rpa/WorkerEnum.php:33` |
| `appType` | `1`（视频号） | `DeviceTaskTrait.php:400` |
| `publish_platform` | `1`（= `DeviceEnum::PUBLISH_PLATFORM_SPH`，取自 `task.account_type`） | `DeviceTaskTrait.php:406`、`DeviceEnum.php:46` |
| `material_id` | `sv_publish_setting_detail.id`（后端据此查明细，见 §2） | `DeviceTaskTrait.php:407` |
| `type`(content 内) | `material_type`：**1 = 视频**（明细只带 1 条 URL）、**2 = 图文** | `app/api/logic/device/PublishLogic.php:1056`（`media_type==1` 取 `url[1]`）、`:184`（`media_type===2` 命名「图文发布任务」） |
| `list` | 素材 URL 数组：图文 = 该分组的全部图片；视频 = 1 条 | `PublishMediaUrlService.php:20-45` |
| `taskId` | `detail.task_id`，32 位 md5，**每次生成明细时新建** | `DeviceTaskTrait.php:415`、`app/common.php:342-345` |
| `isScheduledTime` / `scheduledTime` | 固定 `true` + `detail.publish_time` | `DeviceTaskTrait.php:413-414` |
| `title` / `body` / `tag` | 明细的标题/正文/话题 | `DeviceTaskTrait.php:408/416/417` |
| `isLocation` / `location` | 是否带 POI + POI 值 | `DeviceTaskTrait.php:411-412` |

**说明**：演示/预览链路（`app/api/logic/auto/DeviceLogic.php:470-486`、`:498-515`）在同一 `type=5` 上会多带 `isSend=0`、`isDemoData`、`auto_type`；正式发布**不带**这三个字段。

## 2. 设备 → 后端：回执契约（后端强制校验，不满足即丢弃/判失败）

出口：RPA 事件 `type=14`（`WorkerEnum.php:42` `RPA_MEDIA_STATUS`「图文视频发布状态更新」）
处理：`app/common/workerman/rpa/handlers/MediaStatusHandler.php`

### 2.1 必填与断言

| 校验 | 规则 | 违规后果 | 出处 |
|---|---|---|---|
| `material_id` | 必须能查到**未软删**的 `sv_publish_setting_detail` | 抛「发布回执未匹配素材任务」，整帧丢弃 | `:54-58` |
| `deviceId`（顶层） | 非空且 === `detail.device_code` | 抛「发布回执设备与下发任务不一致」 | `:239-243` |
| `taskId` | 非空且 === `detail.task_id` | 抛「发布回执任务标识与下发任务不一致」 | `:244-246` |
| `publish_platform` | 若 >0 必须 === `detail.account_type`（视频号=1） | 抛「发布回执平台与下发任务不一致」 | `:248-251` |
| `status` | 只能 ∈ `{1=成功, 2=失败, 3=执行中}` | 抛「发布回执状态无效」 | `:235-237` |
| 状态守卫 | `status=3` 仅允许从明细 `status=0` 转移；`status=1/2` 允许从 `0` 或 `3` 转移 | 不命中则按「忽略并发的发布状态回执」丢弃 | `:88-107` |

### 2.2 `status=1`（成功）额外的**数量强校验**（最容易造成「实发成功却记失败」）

- 请求侧 = `PublishMediaUrlService::forPublishDetail()`：优先取 `sv_publish_setting_detail_media` 子表（按 `sort_order`），否则回退旧字段 `material_url`（`PublishMediaUrlService.php:20-45`）。**不排序、不去重**。
- 回执侧 = `forReceipt()`：必须是数组、≤12 项、每项为合法 http(s) URL（`:122-141`）。**不排序、不去重、不允许空项**。
- 判定：`MediaStatusHandler.php:283-287` 用严格 `!==` 比较两者**条数**：不等（少报或多报）即抛 `发布成功回执素材数量与下发任务不一致`。
- 后果：`:83-86` 捕获 → `markInvalidPublishReceipt()` `:295-332` 把明细写成 `status=2`、remark = `发布回执无效：发布成功回执素材数量与下发任务不一致`，并把设备任务置为失败；原始 `published_media` 会存进 `extra.publish_receipt.reported_media`，`published_content` 被丢弃。

### 2.3 `status` 的后端副作用

| 回执 status | 明细 | 设备任务 | 出处 |
|---|---|---|---|
| 1 成功 | `status=1` | 完成 | `:88-96`、`:122-128` |
| 2 失败 | `status=2` | 失败 | 同上 |
| 3 执行中 | `status=3` + `exec_time` | 执行中 | 同上 |

账号/发布设置只在「该账号再无 `status∈[0,3]` 的明细」时才推进为完成（`:345-375`）；**视频号目前没有回执超时兜底**（`DeviceEnum.php:62` 白名单只有快手），因此明细卡在 `3` 时 PC 端会长期显示「进行中」。

## 3. 问题清单（请设备侧逐条回答）

> 「影响」一列写明该答案会决定后端哪段逻辑是否要动，便于双方评估工作量。

| # | 问题 | 为什么问 | 影响 |
|---|---|---|---|
| **Q1** | 设备端是否已支持 `type=5` + `content.publish_platform=1`（视频号）？图文（`type=2`）与视频（`type=1`）是否都已接通？各自入口/前置条件（需登录视频号、需在前台等）？ | 这是「设备端能否执行视频号发布」的总开关 | 若不支持，后端无论怎么改都无法发布 |
| **Q2** | 成功回执 `published_media` 的语义是什么：**请求的素材**还是**实际发布成功的素材**？是否保证条数与下发 `list` **完全相等**？如果实际只能发出 9 张而下发了 12 张，设备会回带几条？ | 后端按条数严格比较（§2.2），少报即把成功判成失败 | 决定是否要把 `MediaStatusHandler.php:283-287` 的判据从「条数必须相等」改为「至少成功 N 条」或「只校验非空」——这是**后端唯一可能需要改的一处**，但要产品同意弱化强校验 |
| **Q3** | 视频（`list` 只有 1 条）发布成功时，回执是否带 `published_media`？带几条？会不会是空数组/字段缺省？ | 若视频不回带该字段，后端会按 `1 !== 0` 把**成功的视频发布判为失败** | 与 Q2 同一处判据；视频是视频号的主力场景，建议优先确认 |
| **Q4** | `taskId` 是否**原样**回带？设备重启、断网重传、命令重试时是否保持不变？设备本地保留多久？ | 后端要求非空且等于明细 `task_id`；编辑发布任务会重建明细并**更换** task_id（`app/api/logic/sv/PublishLogic.php:141-143`） | 若设备会丢/改 taskId，需要在编辑入口禁止「有在途发布时重建」，或后端放宽断言 |
| **Q5** | `material_id` 是否原样回带？ | 后端以 `material_id` 作为唯一查表入口（`MediaStatusHandler.php:54`），查不到即整帧丢弃 | 回错 id = 永远不收敛 |
| **Q6** | 是否会回传 `status=3`（执行中）？频率？是否只在「已开始真实操作」后才发？ | 后端只允许 `0→3`，且 `3` 会把设备任务置为执行中 | 影响是否能在 UI 上区分「已下发」与「设备未响应」 |
| **Q7** | 失败（`status=2`）时 `msg` 是否必带可定位原因？是否带 `imageUrl` 截图？ | 后端直接用 `msg` 落 remark，PC 端排查依赖它 | 影响排障效率 |
| **Q8** | `isScheduledTime=true` + `scheduledTime` 设备端如何处理：设备自己等到点再发，还是立即发？若设备到点前重启会怎样？ | 后端把计划时间下发给设备，不自己等到点（`DeviceTaskTrait.php:413-414`） | 决定「定时发布」是否可靠；也决定超时兜底阈值怎么定 |
| **Q9** | `type=5` 是否支持「只读/试运行」不真发？若支持，字段名与语义？另：演示链路里的 `isSend=0` / `isDemoData`，设备端是怎么解释的？ | 后端目前正式发布不带任何只读字段；`read_only` 只在接管 720-723 等命令族用过（`DeviceTaskTrait.php:1329→:1355/:1368/:1381`） | 决定是否需要新增只读发布能力（可后置） |
| **Q10** | 视频号图文**最多几张图**、视频时长/体积上限？设备端是否有自己的截断策略？ | 后端上限是 12（`PublishMediaUrlService.php:14`），前端/AI 文案上限是 9（`public/pc/_nuxt/publish-panel.a4303c5a.js` 的 `le=9`；`PublishImageCopywritingService.php:55-57`） | 最省事的收口方式：后端按设备/平台真实上限下发（下发数 = 能发数 = 回带数），B2 直接消失，且不必纠结「统一到 9 还是 12」 |

## 4. 自证与排障手册（不改代码即可定位）

按下面 4 种形态对照，基本能在 5 分钟内定位「卡在哪一段」：

| 现象 | 看哪里 | 结论 |
|---|---|---|
| A. 明细 `status=0`，`exec_time=0` | 明细表无 `exec_time`；`runtime/log/device/`（`publish` 级别）无 `RPA [视频号]发布任务[...]` 记录 | **下发就没发生**：设备不在线 / 不在调度器设备集合（`sv_device.auto_type` 与任务 `auto_type` 不匹配）/ 时间窗未到（`DeviceTaskScheduler.php:156-203`） |
| B. 明细 `status=3` 且 `exec_time>0`，长期不动 | `runtime/log/device/` 有 payload 记录；`runtime/log/structured/`（`rpa_handler.event`）可能有 warning | **已下发，回执缺失或被拒**。视频号无超时兜底（`DeviceEnum.php:62` 仅快手），会一直「进行中」 |
| C. 明细 `status=2`，remark 含「发布回执无效：发布成功回执素材数量与下发任务不一致」 | `extra.publish_receipt.reported_media` 与下发的 `list` 条数对比 | **B2/B2′**：设备少报（或视频未回带 `published_media`）——对应 Q2/Q3 |
| D. 明细 `status=2`，remark 是「发布失败」类文案 | `extra.publish_receipt` / 设备任务 remark | 真实失败，看设备的 `msg` |

补充：
- 下发 payload 原文写在 `Log::channel('device')`（`apart_level` 含 `publish`，配置见 `config/log.php:106-113`），文件在 `runtime/log/device/`。
- 回执处理日志走 `AppLogger` → `runtime/log/structured/`（`config/log.php:79-81`）。
- **注意**：结构化「发布回执未生效」warn 目前只对快手输出（`MediaStatusHandler.php:226` + `DeviceEnum.php:62`）。视频号被拒时只能看到明细 remark 和一条 `cron` 级原文日志——这也是原始审计里 B1 的一部分。

## 5. 后端侧「保证能执行」的最小结论

1. **只要 Q1/Q2/Q3 的答案是「设备端已支持、且成功回执按与下发等长回带」，视频号图文/视频即可端到端跑通，后端不需要改任何代码。**
2. 若 Q2/Q3 的答案是「设备只能回带实际发出的条数」或「视频不回带 `published_media`」，则后端**只需改一处**：`app/common/workerman/rpa/handlers/MediaStatusHandler.php:283-287` 的成功回执判据（从「条数严格相等」改为「非空 / 至少 N 条 / 记录差异但不判失败」）。该改动会弱化现有强校验，需要产品确认。
3. 回执超时兜底（B1）与只读发布（B5）都**不是**「能执行」的前置条件，可后置。
4. 上限定标（9 或 12）不必先拍：按 Q10 的答案让**下发张数 = 设备真实能发张数 = 回带张数**即可。
