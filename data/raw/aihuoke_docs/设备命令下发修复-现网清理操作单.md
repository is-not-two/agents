# 现网清理操作单：设备命令下发链路（朋友圈 743 等）

> 适用对象：DBA / 运维 / 后端值班
> 关联修复：`config/device_command.php`（B1'/B2/B2c/B3/B4）、`DeviceCommandService`、`TaskLogic`、`V2DeviceCommandReceiptHandler`、`DeviceTaskScheduler`、`DetectDirtyTask`
> 本操作单只操作 **`sv_device_command` / `sv_device_command_lane` / `sv_device_command_event`** 三张命令账本表；**不修改任何业务表**（`ai_wechat_circle_task`、`sv_device_task` 等），业务状态由代码自身收敛。
> 表前缀按部署实际取（本文以 `la_` 为例）。

---

## 0. 总原则

1. **优先自动、慎用手工**：修复代码自带收敛（B3 收敛 cron）与执行线放行（B1' 持线上限）。手工 SQL 只用于"代码生效前需要立即恢复业务"或"代码判定之外的特例"。
2. **先备份、后写入、可回滚**：任何 UPDATE 前先做行级备份（见 §2）。
3. **顺序不可颠倒**：先让"过期 PENDING"失效，再放行执行线；否则放行瞬间会把历史命令真发出去（现场排队里有 19 小时前的朋友圈文案）。
4. **业务侧删除任务请走业务接口**（已修：删除朋友圈任务会自动作废其 PENDING 命令），不要让 DBA 手工删业务行，否则又会产生孤儿命令。

## 1. 上线与清理顺序

| 步骤 | 动作 | 判定通过条件 |
|---|---|---|
| ① | 部署后端（含 `config/device_command.php`），开关全部保持默认：`converge_stale_mode=dry_run` | `php think` 进程正常；日志出现 `device_command.would_converge` |
| ② | 观察 24h `would_converge` 演练日志 | 与人工判断一致（见 §5） |
| ③ | 切 `DEVICE_COMMAND.CONVERGE_STALE_MODE=write` | 日志出现 `device_command.converged_stale` |
| ④ | 放行历史 lane（B1' 自动，或 §6 手工兜底） | `sv_device_command_lane.current_request_id` 变空 |
| ⑤ | 复跑体检 SQL（§3）确认归零 | 三类异常计数均为 0（历史数据可留档） |
| ⑥ | 设备端新版本发布（D1/D2'） | 真机回归通过 |

> 部署后即生效的默认项：`lane_max_hold_seconds=21600`、`sweep_lane_stale_by_create_time=true`、`sweep_pending_backlog=true`、`pending_max_age=1800`、`lane_held_log_interval=300`、`circle_timeout_settles_command=true`（朋友圈专项，见 §6）。
> 开关都可一键回退：改 `.env` 的 `DEVICE_COMMAND_*` 或 `config/device_command.php` 后清理 `runtime/cache`。

## 3. 体检 SQL（盘点 + 验收，同一套）

```sql
-- A. 谁在锁谁：被占用的执行线 + 积压条数
SELECT l.device_id, l.current_request_id, c.command_type, c.status,
       c.accepted_at, c.running_at, c.last_progress_at, c.uncertain_at,
       FROM_UNIXTIME(c.create_time) ct, FROM_UNIXTIME(c.update_time) ut,
       (SELECT COUNT(*) FROM la_sv_device_command p
         WHERE p.device_id = l.device_id AND p.status = 0) AS pending_backlog
FROM la_sv_device_command_lane l
JOIN la_sv_device_command c ON c.request_id = l.current_request_id
WHERE l.current_request_id IS NOT NULL
ORDER BY pending_backlog DESC;

-- B. 建了从没派发（真正意义上的"收不到命令"）
SELECT device_id, command_type, COUNT(*) cnt, FROM_UNIXTIME(MIN(create_time)) oldest
FROM la_sv_device_command WHERE status = 0
GROUP BY device_id, command_type ORDER BY cnt DESC;

-- C. 派发后无终态（平台级，跨业务类型）
SELECT command_type, status, COUNT(*) cnt,
       FROM_UNIXTIME(MIN(create_time)) oldest, FROM_UNIXTIME(MAX(update_time)) newest
FROM la_sv_device_command WHERE status IN (1,2,3,7)
GROUP BY command_type, status ORDER BY cnt DESC;

-- D. 孤儿命令（朋友圈：母任务已不存在）
SELECT c.request_id,c.device_id,c.status,c.attempt_count,c.business_task_id,
       FROM_UNIXTIME(c.create_time) ct
FROM la_sv_device_command c
LEFT JOIN la_ai_wechat_circle_task t ON t.task_id = c.business_task_id
WHERE c.command_type='wechat.publish_circle' AND c.status NOT IN (5,6) AND t.id IS NULL
ORDER BY c.create_time;

-- E. 只读脏数据扫描（代码内置，可选，最全）
php think detect:dirty_task
```

**2026-09-30 现场基线（供比对，验收时这些应全部消失）**
- A：1 台被占——`AHKD4536E133E0D` / `689828b75945c1553a10d2f2c16c6175`（`wechat.publish_circle`，status=7，`last_progress_at` 持续刷新，积压 2）
- B：`AHKD4536E133E0D` 2 条（09-29 15:27 起）、`wxid_tdohzxqfk9gw19` 6 条（09-21 起，设备在 `sv_device`/授权/`ai_wechat_device` 中均已不存在）
- C：`takeover.stop` 7、`private_message.send` 4、`wechat.publish_circle` 7（status 7/2）
- D：8 条朋友圈孤儿（`AHKD4536E133E0D` 6 + `AHK429C1A2D1F62` 2）

## 4. 作废"过期未派发"命令（防误发）

**优先方式：交给业务/代码。**
- 朋友圈：走业务接口删除该朋友圈任务 → 新版 `TaskLogic::deleteTask` 会自动 `PENDING → FAILED(cancelled)`（见 `settleCircleCommandsOnDelete`）。
- 其它业务：走对应任务删除/中断入口，或等 B3 收敛（`pending_stale_seconds=600`）自动置 `undelivered_timeout`。

**手工兜底（仅在需要立即恢复、且业务确认这些命令不该再执行时）：**

```sql
-- 4.1 先看清楚要作废什么（务必人工逐条确认"业务上确实不需要再执行"）
SELECT request_id, device_id, command_type, business_task_id,
       FROM_UNIXTIME(create_time) ct,
       TIMESTAMPDIFF(HOUR, FROM_UNIXTIME(create_time), NOW()) age_hours
FROM la_sv_device_command
WHERE status = 0
ORDER BY create_time;

-- 4.2 作废（示例：只作废 2026-09-29 之前创建、且设备可辨认的两台）
UPDATE la_sv_device_command
SET status = 6,
    result_code = 'undelivered_timeout',
    result_message = '人工清理：命令长期未派发（执行线占用/设备未就绪），作废以免过期内容迟发',
    finished_at = UNIX_TIMESTAMP(),
    update_time = UNIX_TIMESTAMP()
WHERE status = 0
  AND create_time < UNIX_TIMESTAMP('2026-09-30 00:00:00')
  AND device_id IN ('AHKD4536E133E0D','wxid_tdohzxqfk9gw19');
-- 期望：affected = 8（现场 2 + 6）

-- 4.3 留痕（可选，便于后续审计）
INSERT INTO la_sv_device_command_event (request_id, event_id, event_type, payload, create_time)
SELECT request_id, CONCAT('manual-cleanup-', request_id), 'undelivered_timeout',
       JSON_OBJECT('message','manual cleanup: stale pending cancelled','by','ops-cleanup-20260930'),
       UNIX_TIMESTAMP()
FROM la_sv_device_command
WHERE result_code = 'undelivered_timeout' AND finished_at >= UNIX_TIMESTAMP() - 600;
```

回滚：`UPDATE ... SET status=0, result_code='', result_message='', finished_at=0 WHERE result_code='undelivered_timeout' AND create_time < ...`（范围必须与备份表 `bak_cmd_nonterminal_20260930` 逐行核对）。

## 6. 放行历史执行线（朋友圈专项 → B1' 自动 → 手工兜底）

**朋友圈专项（最快路径，默认开启 `circle_timeout_settles_command=true`）**：
朋友圈任务在 `end_time+300` 被判失败的同一步，调度器会收敛该任务对应的在途命令（`result_code=business_timeout`）并放行执行线。日志：`device_command.circle_business_timeout_settled`（另有一条 `setTaskLog` 中文摘要）。
这条是"朋友圈执行线堵塞"的主解法：743 的终态由跑几分钟的 OCR 内核产生，一旦内核被取消/挂死，命令会带 accepted 证据停在非终态、按统一规则要持线 6 小时，而朋友圈业务 5 分钟就判失败；有了这条，持线时间被压缩到 `end_time+300 + 一个调度周期`。设备端新版本另有 15 分钟执行看门狗（D2'）在设备侧兜底。

**自动路径（通用）**：部署后 `lane_max_hold_seconds=21600` 生效，`sweepStalledLanes` 会按 `create_time` 把陈旧 lane 纳入巡检，`releaseStalledLane` 对超限命令：
- 置 `status=6 / result_code=lane_max_hold_exceeded`；
- 追加事件 `lane_max_hold_exceeded`；
- 清空 `sv_device_command_lane.current_request_id`；
- `sv_device_command` 侧同时留下 `finished_at`。

日志：`device_command.lane_max_hold_exceeded`，同时每 5 分钟可见 `device_command.lane_held`（占用期诊断）。

**手工兜底（仅当自动未按预期发生，且已确认设备侧不会再上报终态）：**

```sql
-- 6.1 先确认目标（务必先跑 §3-A）
SELECT l.device_id, l.current_request_id, c.status, c.create_time,
       TIMESTAMPDIFF(HOUR, FROM_UNIXTIME(c.create_time), NOW()) age_hours
FROM la_sv_device_command_lane l
JOIN la_sv_device_command c ON c.request_id = l.current_request_id
WHERE l.current_request_id IS NOT NULL;

-- 6.2 收敛命令（示例：仅针对现场那一条）
UPDATE la_sv_device_command
SET status = 6, result_code = 'lane_max_hold_exceeded',
    result_message = '人工清理：执行线长期被占且设备无真实终态',
    finished_at = UNIX_TIMESTAMP(), update_time = UNIX_TIMESTAMP()
WHERE request_id = '689828b75945c1553a10d2f2c16c6175'
  AND status IN (0,1,2,3,4,7);

-- 6.3 放行执行线（条件更新，避免误清别人的 lane）
UPDATE la_sv_device_command_lane
SET current_request_id = NULL, update_time = UNIX_TIMESTAMP()
WHERE device_id = 'AHKD4536E133E0D'
  AND current_request_id = '689828b75945c1553a10d2f2c16c6175';
```

放行后**必须先确认 §4 已完成**：否则队列里那些 09-29 的过期命令会被 B2c 拦下（默认 `pending_max_age=1800` 生效），但一旦有人把 `PENDING_MAX_AGE=0`，就会真发出去。

## 9. 注意事项与残余风险

1. **不要手工改设备端本地 Outbox**：设备 `v2_outbox` 只能由后端 840 确认或本地清理删除。新版后端已把"迟到终态回执"改为幂等确认（`device_command.late_terminal_receipt`），不会再因 error 造成永久重发。
2. **收敛为 FAILED 会挡住设备迟到的真实终态**（`processReceipt` 对已终态命令拒绝新事件）。因此：
   - B1'（6h 持线上限）与 3a/3b 属于"业务对象已消失或从未派发"，风险可接受；
   - 3c（`inflight_max_age`）默认**关闭**，是否开启需产品确认"迟到 succeeded 是否要纠偏业务"（当前设计不接受纠偏）。
3. **`pending_max_age=1800` 是安全阀**：任何情况下不要为了让历史命令发出去而把它设为 0；确需补发请重新建业务任务。
4. **微信朋友圈"空文案"仍会真机发出后判失败**（既有契约：后端成功回执要求正文非空）。本次修复未改该行为，属于待产品决策项；若确认要禁止，应在创建侧拦截（已明确划归前端方案）。
5. 命令号段：设备端只处理 `720..845` 的 V2 帧；若后续调整号段，需同步设备端过滤范围。
6. **朋友圈专项收敛的副作用（需知悉）**：`circle_timeout_settles_command` 在任务判失败时立即放行执行线。若设备此刻其实**仍在真机发布**（例如网络极慢、内核尚未走完），放行后若有新的朋友圈命令进入，设备端 `StepManager.cleanup()` 会取消在途内核，那次发布会被中止（最多停留在编辑页、不会发出半条朋友圈）。业务上该任务已被判失败，且设备端 15 分钟看门狗本来也会做同样的事，故可接受；若某环境对这种"临门中止"敏感，可设 `CIRCLE_TIMEOUT_SETTLES_COMMAND=false` 回退到 6 小时持线上限（B1'）。
