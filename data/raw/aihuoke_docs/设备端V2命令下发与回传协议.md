# 设备端 V2 命令下发与回传协议

版本：`V2`  
适用端：小红书、抖音、快手、个微接管、评论获客及个微 AI 回复。  
生效原则：设备端仅以本协议的 V2 指令号执行动作；旧 `6/7/12/13/30/31/32/101-107/603/610/611` 不得用于新的接管、私信或评论任务。

## 1. 必须遵守的规则

1. 后端生成 `requestId`，设备端不得自行生成或改写。它是一次设备动作的唯一标识，格式为 32 位十六进制字符串。
2. 同一设备的 V2 命令由后端按 `sequence` 串行下发。设备端必须完成当前命令并发送终态回执后，才会收到下一条命令。
3. `accepted`、`succeeded`、`failed` 都表示设备已经实际执行到对应阶段，绝不能在“收到报文”“进入页面”或“准备重试”时伪造成功。
4. 设备断线、应用异常、页面找不到账号、发送失败、执行结果不完整，必须回传 `failed` 和明确错误信息；不能以超时或本地猜测回传 `succeeded`。
5. 重传同一设备动作时，`requestId` 与 `eventId` 必须保持不变。后端以二者去重，重复回传不会重复执行或重复写成功。
6. V2 回执为单向上行。后端不会把 `820-839` 原样回送给设备端；设备端不得等待该类回执的同号 ACK。

## 2. RPA JSON 下发信封

RPA 平台命令通过 `device.{deviceId}.message` 下发。`content` 是 JSON 字符串，需先反序列化。

```json
{
  "type": 720,
  "requestId": "b33d1a7f3d5b0af96252c2a6a4cd5e17",
  "deviceId": "device-001",
  "appType": 3,
  "account": "xhs_account",
  "sequence": 18,
  "status": "dispatch_attempted",
  "errorCode": "",
  "errorMessage": "",
  "content": "{\"taskId\":123,\"deviceId\":\"device-001\",\"account\":\"xhs_account\"}"
}
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 是 | 本协议中的下发指令号。|
| `requestId` | 是 | 后端唯一动作 ID，所有回执原样回带。|
| `deviceId` | 是 | 目标设备，回执必须完全一致。|
| `appType` | 是 | `1=个微`、`3=小红书`、`4=抖音`、`5=快手`。|
| `account` | 是 | 目标账号，回执必须完全一致。|
| `sequence` | 是 | 当前设备执行线序号，只用于日志与排查。|
| `content` | 是 | JSON 字符串，包含业务动作参数。|

## 3. 下发命令

### 3.1 私信接管

| 下发 type | 平台 | 操作 | `content` 关键字段 | 成功回执 |
| --- | --- | --- | --- | --- |
| `720` | 小红书 | 启动接管 | `taskId, deviceId, account, accountType, startTime, endTime, readOnly` | `820 accepted` |
| `721` | 抖音 | 启动接管 | 同上 | `821 accepted` |
| `722` | 快手 | 启动接管 | 同上 | `822 accepted` |
| `723` | 个微 | 启动接管/个微 RPA | `taskId` 或 `task_id`、账号、时间、个微策略参数 | `823 accepted` |
| `724` | 小红书 | 停止接管 | `taskId, deviceId, account, accountType` | `824 succeeded/failed` |
| `725` | 抖音 | 停止接管 | 同上 | `825 succeeded/failed` |
| `726` | 快手 | 停止接管 | 同上 | `826 succeeded/failed` |
| `727` | 个微 | 停止接管/个微 RPA | 同上 | `827 succeeded/failed` |

启动命令的 `accepted` 含义是：设备已经确认目标账号、接管配置和页面状态均可用，并已经实际启用接管。后端收到后才会将业务任务切为“运行中”。

收到停止命令后，设备必须真实关闭本次 `requestId` 对应的接管流程、停止相关轮询/输入动作，再回传 `succeeded`。停止失败须回传 `failed`，后端会保留任务失败态，不会自动完成。

### 3.2 平台私信回复

| 下发 type | 平台 | 回传 type |
| --- | --- | --- |
| `728` | 小红书 | `828` |
| `729` | 抖音 | `829` |
| `730` | 快手 | `830` |

`content` 结构：

```json
{
  "reply": {
    "type": 1,
    "content": ["第一段", "第二段"],
    "link": "",
    "targetRecipient": "接收方标识",
    "lastMessageContent": "触发回复的最后一条消息",
    "reply_files": [],
    "requestId": "与顶层 requestId 相同"
  },
  "sourceMessageIds": [1001, 1002],
  "sourceMessageId": "设备上报的新消息标识"
}
```

设备端必须按数组顺序发送 `reply.content`，并在所有内容均真实发出后回传 `succeeded`。任一内容未成功发送时，整条命令回传 `failed`，不得只回报部分成功。后端仅在 `828-830 succeeded` 后写入消息已回复状态和回复日志。

### 3.3 评论获客/评论区私信/留痕

| 下发 type | 平台 | 操作 | 回传 type |
| --- | --- | --- | --- |
| `736` | 小红书 | 评论检索及实际动作 | `836` |
| `737` | 抖音 | 评论检索及实际动作 | `837` |
| `738` | 快手 | 评论检索及实际动作 | `838` |

下发 `content` 为任务原始参数，包含 `task_id`、账号、检索词、筛选条件、数量限制、评论内容及实际动作开关。设备端不能因检索到页面或候选数据而宣布成功；必须先完成全部需要执行的点赞、关注、评论、私信或留痕动作。

成功回执的 `resultData` 必须包含逐条结果和任务汇总：

```json
{
  "actionResults": [
    {
      "record_id": 501,
      "task_id": 88,
      "task_type": 3,
      "status": 1,
      "touch_content": {"like": true},
      "avatar": "https://...",
      "remark": ""
    }
  ],
  "taskResult": {
    "task_id": 88,
    "result": "success",
    "execution_started_at": "2026-08-29 10:00:00",
    "execution_finished_at": "2026-08-29 10:05:00",
    "scan_count": 20,
    "matched_count": 3,
    "reported_count": 3,
    "success_count": 3,
    "failed_count": 0,
    "summary_by_keyword": [],
    "clue_verification_summary": []
  }
}
```

逐条 `status`：`1=成功`，`0` 或 `2=失败`。后端会按 `record_id/task_id/deviceId/task_type` 校验归属，并将设备汇总与已入库逐条结果对比；数量不一致、存在未完成或失败动作时，任务会被判失败，即使顶层状态传了 `succeeded`。

### 3.4 会话列表与名片

| 下发 type | 平台 | 操作 | 回传 type |
| --- | --- | --- | --- |
| `731` | 小红书 | 获取完整会话列表 | `831` |
| `732` | 抖音 | 获取完整会话列表 | `832` |
| `733` | 快手 | 获取完整会话列表 | `833` |
| `734` | 小红书 | 获取完整名片列表 | `834` |
| `735` | 小红书 | 发送指定名片 | `835` |

会话列表和名片查询的下发 `content` 都会带 `snapshotMode: "full"`。设备端必须完成本次可见范围内的完整采集后，才可回传 `succeeded`；分页未结束、页面加载失败或只能得到局部数据时，回传 `failed`。

会话快照 `831-833` 的 `resultData`：

```json
{
  "complete": true,
  "snapshotId": "device-local-snapshot-20260829-01",
  "items": [
    {
      "authorName": "会话对象",
      "messageContent": "最后一条消息",
      "messageTimer": "2026-08-29 10:00:00",
      "newMessageCount": 2,
      "replyObject": "",
      "customerType": 1,
      "avatar": "https://..."
    }
  ]
}
```

`complete` 必须为 `true`；每个会话项必须有 `authorName`、`messageContent` 和 `messageTimer`。后端先将原始完整快照按 `requestId` 持久化，再按账号/会话/消息时间幂等更新会话消息，最后才将命令置为成功并通知 Web。

名片查询 `834` 的 `resultData`：

```json
{
  "complete": true,
  "snapshotId": "card-snapshot-01",
  "cards": [
    {"cardId": "...", "name": "...", "content": {}}
  ]
}
```

名片发送 `835` 的 `resultData`：

```json
{
  "complete": true,
  "targetRecipient": "接收方标识",
  "deviceMessageId": "设备侧消息标识"
}
```

后端会保存完整名片快照或发送结果，并且仅在 `835 succeeded` 后通知 Web 名片已发送。

## 4. V2 回传信封

设备端向 RPA Socket 上报时，顶层字段必须如下。`content` 可省略；如带入，只能是 JSON 对象或 JSON 字符串，且其中的 `requestId` 必须等于顶层值。

```json
{
  "type": 828,
  "requestId": "b33d1a7f3d5b0af96252c2a6a4cd5e17",
  "deviceId": "device-001",
  "appType": 3,
  "account": "xhs_account",
  "eventId": "send-result-b33d1a7f-1",
  "status": "succeeded",
  "resultCode": "",
  "resultMessage": "",
  "resultData": {}
}
```

| 字段 | 要求 |
| --- | --- |
| `requestId` | 必须来自对应下发信封，不能为空。|
| `deviceId/appType/account` | 必须与下发命令完全一致，不一致的回执会被拒绝。|
| `eventId` | 当前设备事件的稳定唯一 ID。网络重传使用原值；新事件必须更换。|
| `status` | 仅允许 `accepted`、`running`、`succeeded`、`failed`，并受下表限制。|
| `resultCode` | 设备错误码或空字符串。|
| `resultMessage` | 失败时必填、可定位的原因。|
| `resultData` | 评论任务按 3.3 传递；其他任务按需提供可审计执行结果。|

回传 type 与状态限制：

| 回传 type | 对应下发 | 允许 `status` | 含义 |
| --- | --- | --- | --- |
| `820/821/822/823` | `720/721/722/723` | `accepted`、`failed` | 接管启动确认或启动失败。|
| `824/825/826/827` | `724/725/726/727` | `succeeded`、`failed` | 接管停止的真实终态。|
| `828/829/830` | `728/729/730` | `succeeded`、`failed` | 平台私信发送的真实终态。|
| `831/832/833` | `731/732/733` | `succeeded`、`failed` | 完整会话快照终态；成功必须带完整 `items`。|
| `834` | `734` | `succeeded`、`failed` | 完整名片快照终态；成功必须带完整 `cards`。|
| `835` | `735` | `succeeded`、`failed` | 名片发送真实终态。|
| `836/837/838` | `736/737/738` | `succeeded`、`failed` | 评论任务真实终态；成功必须带完整 `resultData`。|
| `839` | 对账专用 | `succeeded`、`failed` 或未知状态 | 仅在后端发起对账后使用，不作为普通任务回执。|

## 5. 个微 protobuf 私信回复

个微 AI 回复使用既有 `socket.{deviceId}.message` protobuf 通道，消息类型为 `TalkToFriendTask`，不使用 RPA JSON 信封。

后端会设置：

```text
TalkToFriendTask.TaskId = requestId
TalkToFriendTask.MsgId  = requestId
```

设备端必须在 `TalkToFriendTaskResultNotice` 原样回传该 `MsgId`。后端以 `MsgId` 关联命令账本：

- `Success=true`：写入发送成功，并推进同设备下一条命令；
- `Success=false`：写入失败，保留 `Code/ErrMsg`，不伪造成功；
- 重传同一结果通知时，`MsgId`、`MsgSvrId`、`Code` 保持一致。

## 6. 禁止复用的旧协议

- `type=6/7`：不得再作为平台私信或名片发送指令；平台私信使用 `728-730`。
- `type=12/13`：不得作为 V2 锁、启动或完成回执；V2 以 `requestId + eventId + 终态回执` 管理唯一性。
- `type=30/31/32`：不得用于接管启动、结束或结果；接管使用 `720-727` 和 `820-827`。
- `type=101-107`：不得用于新的评论任务下发或 V2 终态；评论使用 `736-738` 和 `836-838`。
- `type=603/610/611`：不得再用于会话列表、名片查询或名片发送；对应 V2 指令固定为 `731-735`。

## 7. 失败、断线与恢复

1. 设备无法执行时立即上报 `failed`，不得等待后端超时。
2. 后端超时不会自动成功、不会自动释放设备执行线，也不会推进父任务；任务将保持待对账或失败状态。
3. 设备恢复后，只有收到相同 `requestId` 的明确真实结果，后端才会结束该命令并下发下一条。
4. 不允许通过更换 `requestId` 重试旧命令。需要人工或后端显式创建新的业务任务后，才会生成新的 `requestId`。
