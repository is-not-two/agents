日期：2026-09-16
背景：确认「微信接管 AI 回复」桩调用后，需要明确**设备指令到底走哪条通道**，以便决定
`WechatAcceptFriendJob` / `WechatSendCircleJob` 两处桩的实现方式。

> **2026-09-16 收尾（本文档已同步）**：上述两处桩及整条 Jubo 好友链路已完成清理，
> 相关类**均已删除**：`WechatAcceptFriendJob`、`WechatSendCircleJob`、
> `app/common/service/ai/WechatService.php`（整个类）、`WechatTrait::wxAccept()`、
> `AcceptFriendAddRequestTaskHandler`。文内提及这些名字处均标注为「已删除」。

## 1. 通道定义（代码事实）

| 通道 | 传输 | 服务端出口 | 设备侧契约 | 消费方 |

| **WeChatPad** | HTTP 网关 | `WechatPadClient`（需 `config('wechatpad.enabled')`） | 网关 REST | `app/api/controller/wechat/*`（小程序 / Web 控制台） |
| **Jubo / Hook** | Channel `socket.{deviceId}.message` | `WechatTrait::wxPush/wxCircle`（`wxAccept` **已删除**） | protobuf（`TalkToFriendTask` / `PostSNSNewsTask`；`AcceptFriendAddRequestTask` **已删除**） | `start_wechat.php` → Jubo 设备 |

证据：
- RPA 出口：`app/common/workerman/rpa/RpaSocketService.php:685-691`（`sendChannelMessage`）、
  `app/common/traits/DeviceTaskTrait.php:508-512`（发圈）、`:993-997`（加好友）。

## 2. 通道划分政策（用户 2026-09-16 确认）

> **自动化 / 服务端直接下发的设备指令 → RPA 通道。**
> **小程序和 Web 网页手动操控微信 → WeChatPad 通道。**

## 5. 三处与政策/可用性不符的地方

### 5.1 `WechatAcceptFriendJob`（自动通过好友）—— 最严重

> **2026-09-16 更正**：本节此前写「`app(ToolsServiceClient::class)` 解析为 `app\common\Jobs\ToolsServiceClient`，
> 类不存在 → 抛错」。**该结论错误**。`WechatAcceptFriendJob.php:9` 有
> `use app\common\service\ToolsServiceClient;`，因此 `ToolsServiceClient::class` 展开为
> `app\common\service\ToolsServiceClient`，**该类存在、可解析、不抛错**。
> 真实缺陷比「报错」更隐蔽，见下。

- 派发方（**当时**）：`FriendLogic.php:297` `Queue::later(..., WechatAcceptFriendJob@fire, ...)`（有效）。
  **2026-09-16：该派发行已移除，Job 类已删除**（`FriendLogic::acceptFriend` 改走 WeChatPadPro 票据流程）。
- `:124` → `app(ToolsServiceClient::class)->wechat->accept(...)` 解析正常，最终落到
  **`app/common/service/ai/WechatService.php:29 accept()` —— 一个服务桩**：
  ```php
  return $this->unavailable('WeChat accept has no confirmed MobileAgent type');
  // → ['code' => 0, 'data' => [], 'msg' => 'SERVICE_UNAVAILABLE: ...']
  ```
- `sendMessage()` 声明为 `void`，**把返回值整个丢掉**，`fire()` 里既不校验 `code` 也不校验 `msg`
  → **Job 静默 no-op**（设备端完全没收到任何指令）。
- 更糟的是：no-op 之后 `fire()` 仍然执行
  `AiWechatLog::create([... 'log_type' => AiWechatLog::TYPE_ACCEPT_FRIEND])`
  → **写了一条假的成功账**。后果有两个：
  1. 前端/日志显示「已通过」，实际没通过；
  2. `FriendLogic::acceptFriend` 的当日额度判定（`AiWechatLog` 计数）被假账消耗，
     `accept_numbers` 上限会被空跑吃满。
- 这与本项目「`WechatService::chat()` 桩返回 `code=0` 导致上游误判成功」是**同一类陷阱**
  （同一文件、同一 `unavailable()` 写法）。

- **RPA 侧确实没有可用契约**（三重证据）：
  1. `DeviceCommandEnum` 里 `COMMAND_WECHAT_ACCEPT_FRIEND='wechat.accept_friend'` / `TYPE_WECHAT_ACCEPT_FRIEND=740` /
     `TYPE_WECHAT_ACCEPT_FRIEND_RESULT=843` **仅占位**，全仓除枚举定义外**零引用**。
  2. `docs/RPA微信命令与事件协议v0.md` §6.3 / §7.5 / §10 三处明确：
     「RPA 命令 `740` 与回执 `843` 仅保留号段，**不创建、不 dispatch、不接入业务副作用**」，
     自动通过好友**继续经 Jubo**（`AcceptFriendAddRequestTask`）落地。
  3. `WechatFriendRequestHandler`（RPA 事件 `type=56`）收到加好友请求后固定返回
     `{action: 'defer', remark: '自动通过好友当前经 Jubo 通道处理，RPA accept_friend 不 dispatch'}`。
- 另外：`WechatTrait::wxAccept()`（原 `WechatTrait.php:471`，Jubo 真实实现）**当前零调用方**，
  已于 2026-09-16 **删除**。

→ 要按 RPA 政策迁，必须先完成：注册并**由微信团队书面确认**命令号段 → 实现设备端
→ 与 Jubo 的 `AiWechatLog TYPE_ACCEPT_FRIEND` 记账**互斥/幂等**（否则双拍）。
**RPA 通道当前不可下发**——但按用户 2026-09-16 决策，自动通过好友**改走 WeChatPadPro**（见 §7），
不再等 RPA 号段。

✅ **2026-09-16 已处理**：
1. `fire()` 现在校验 `sendMessage()` 的返回值，`code !== 10000`（服务约定成功码，桩返回 `0`）
   即抛异常，走既有的 `retryJob` → 3 次后 `markAsFailed`，**不再空跑后写成功账**；
   `sendMessage()` 由 `void` 改为返回结果数组。
2. `FriendLogic::acceptFriend` 已不再 `Queue::later()` 派发本 Job → **本类现已无任何派发方**，
   随后于 2026-09-16 收尾中**整体删除**。

### 5.3 `WechatTrait::wxCircle()` 的非 WeChatPad 分支回落 Jubo

## 7. WeChatPadPro 接口规范（好友申请）

来源：网关 swagger（`https://wechat.cherunbao.com`；核对用临时落盘文件使用后已清理）。
所有接口统一 `POST /api/{Group}/{Action}`，Header 注入 `X-Access-Token`（`WechatPadClient.php:340`），
query 可选 `authcode`（本部署 token 与 authcode 同源）。响应统一包装
`{Code, Data, Message, Success, request_id}` —— **成功判据是 `Code == 0 && Success == true`**
（`WechatPadFriendService::data()` 内再校验 `Data.BaseResponse.ret == 0`）。

### 7.1 `POST /Friend/GetFriendRequestList` — 拉取待处理好友申请

请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `limit` | int | 否 | 每页数量，范围 **1–100**，默认 20 |
| `page` | int | 否 | 页码，从 **1** 开始，默认 1 |
| `status` | string | 否 | `pending` / `accepted` / `all`，默认 `pending` |

响应 `Data`：`{ items: [...], limit, page, total, has_more }`，`items[]` 每项含
`id`（申请 ID，形如 `fr_8a2d3c4e…`）、`display_name`、`greeting`、`received_at`（时间戳）、
`scene`、`status`，以及 **`accept_body`**（即 PassVerify 要用的凭据）。

> 文档原文：「申请由 **msg_type=37** 同步消息自动进入列表。默认只返回 pending，
> **v1/v2/scene 可直接用于 PassVerify**。」

### 7.2 `POST /Friend/PassVerify` — 通过好友申请

请求体（**三个字段全部必填**）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `v1` | string | ✅ | 取自 `friend_request.accept_body` |
| `v2` | string | ✅ | 取自 `friend_request.accept_body` |
| `scene` | int | ✅ | 好友申请来源场景，例 `17` |

成功响应：`{"Code":0,"Data":{"result":true},"Message":"成功","Success":true}`。

> 文档原文注意事项：
> 1. v1/v2/scene **直接使用 `type=37` 好友申请实时事件的 `friend_request.accept_body`**，底层固定 `Opcode=3`；
> 2. **重复提交返回 HTTP 429 时请遵循 `Retry-After`，不要换 v1/v2 重发**。

### 7.3 `POST /Friend/SendRequest` — 主动添加好友（对照用）

请求体推荐 `sourceContext`（一次性，取 Search 返回的 `source_context`）；兼容旧路径
`v1` + `v2` + `scene`（必须**同时**提供）；`opcode` 例 `2`；`verifyContent` 为验证说明。
成功响应同为 `{"Code":0,"Data":{"result":true},...}`。

### 7.4 `POST /User/FriendVerification` — 加我时是否需要验证（**易混淆，非通过接口**）

文档原文特别声明：「微信『我→设置→朋友权限→加我为朋友时需要验证』的专用接口……
**这不是「通过好友申请」接口，也不是朋友圈可见权限**。」
即它是「是否需要验证」开关，与自动通过好友无关，不要拿它当自动通过的实现。

### 7.5 代码侧参数流转（已对齐规范）

`WechatPadFriendService::requests()`：`accept_body` 兼容 `item.accept_body` →
`item.friend_request.accept_body` → 退化到 item 自身取 `v1/v2/scene`；
经 `verifyBody()` 校验（v1/v2 非空、scene ∈ [0,100000]）后签发一次性 ticket
（redis `wechatpad:friend:ticket:{ticket}`，TTL 300s），再交由 `execute()` 调用 `PassVerify`。
`execute()` 用 `wechatpad:friend:action:{hash}` 做**同凭据只投递一次**的幂等保护，
并区分 `success` / `failed` / `unknown`（网络不明时提示「勿重复提交」）——与文档的 429 约束一致。

> ⚠️ **未验证风险（INFERRED）**：swagger 的 `GetFriendRequestList` **响应示例**里
> `items[]` 只列了 `display_name / greeting / id / received_at / scene / status`，
> **没有 `accept_body`**；而文档正文又说 v1/v2 可直接用于 PassVerify。
> 若实际网关不返回 `accept_body`，`verifyBody(item)` 会因 v1/v2 为空返回 `null`
> → `can_accept=false`，前端提示「申请凭据不完整，请刷新申请列表」，自动通过会全部空转。
> **上线前需用真实响应核对一次 `items[].accept_body` 是否存在。**
